# Plan — slice 7: least-privilege app DB role (activates RLS enforcement)

Spec: docs/superpowers/specs/2026-06-27-app-role-design.md
Branch: realwiring-app-role

Mostly DDL + CI proof + runbook; no application code change (the app already sets the GUC and reads
DATABASE_URL). Enforcement is provable only against real Postgres, so the eval is the CI `db` job.

1. **Migration** — `db/migrations/0004_app_role.sql`: create role `app_rw`
   (NOLOGIN/NOSUPERUSER/NOBYPASSRLS, no password — secret-free), grant least privilege
   (USAGE on schema + CRUD on the app tables + matching default privileges). Idempotent.

2. **CI eval (the proof)** — extend the `db` job: enable an `app_rw` login with a CI-only password;
   run ingest (both passes) + retrieval **as `app_rw`** (the real production path, a non-superuser
   subject to RLS); add an "app role is subject to RLS" step asserting `app_rw` is not
   superuser/bypassrls, sees 0 rows with no tenant GUC (fail-closed), and the demo tenant's 5 teams
   with it. Owner-run steps (migrations, verify rows, isolation probe) stay as `postgres`.

3. **Runbook** — `docs/db/app-role.md`: the operator steps to add `LOGIN PASSWORD` and repoint the
   live `DATABASE_URL` at `app_rw` (session pooler only), with verification.

4. **Verify** — offline suite + ruff stay green (no Python change); push the branch and confirm the
   CI `db` job is GREEN (proves the app works as the least-privilege role under enforced RLS); then
   an independent review; then merge.

## Decisions
- Policy NOT scoped `TO app_rw`: the PUBLIC policy already denies anon (NULL GUC -> 0 rows), and
  `TO app_rw` would lock the owner out of its own tables. Keep PUBLIC + this role.
- No password in git: the role is NOLOGIN in the migration; the operator/CI grants login+password.

## Deferred
- The live Supabase switch (operator step). CI proves the role/grants/RLS logic.
- A separate read-only role; multi-tenant provisioning.
